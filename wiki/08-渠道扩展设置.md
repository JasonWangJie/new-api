# 渠道扩展设置（ChannelOtherSettings）

本页说明渠道接口字段 `settings` 对应的 `ChannelOtherSettings` JSON。字段定义以 [`relaykit/dto/channel_settings.go`](../relaykit/dto/channel_settings.go) 为准；上游异步规则还应同时参考 [`relaykit/dto/upstream_async.go`](../relaykit/dto/upstream_async.go)。

## 1. 先区分 `setting` 和 `settings`

渠道对象中有两个名称非常接近、但用途不同的 JSON 字符串：

| 渠道接口字段 | Go 类型 | 主要内容 |
| --- | --- | --- |
| `setting` | `ChannelSettings` | 任务插件、代理、HTTP 协议、系统提示词、图片参考图容量、整包透传等运行设置 |
| `settings` | `ChannelOtherSettings` | 本页说明的供应商开关、字段透传控制、模型发现、Advanced Custom 和上游异步解析 |

本页所有示例都先展示 `settings` 字符串解码后的 JSON 对象。例如，文档中的：

```json
{
  "allow_service_tier": true,
  "tool_loss_policy": "safe"
}
```

通过渠道 REST 接口提交时，`settings` 本身仍是一个 JSON 字符串：

```json
{
  "id": 12,
  "settings": "{\"allow_service_tier\":true,\"tool_loss_policy\":\"safe\"}"
}
```

`PUT /api/channel/` 是渠道更新接口，不是只修改 `settings` 的独立 PATCH。直接调用接口前应先读取现有渠道，保留其余可写字段，只替换 `settings`；更推荐通过管理后台的渠道编辑表单配置。不要直接修改数据库。

空对象 `{}` 表示全部使用默认行为。只配置实际需要的字段，不要为了“完整”复制所有开关。

## 2. 顶层字段总表

| JSON 字段 | 类型与默认值 | 适用范围 | 含义 |
| --- | --- | --- | --- |
| `azure_responses_version` | `string`，默认空 | Azure | 覆盖 Responses 与 Responses Compact 请求中的 `api-version`。留空时使用适配器根据 Azure 地址得到的默认版本。只填写目标 Azure 端点真实支持的版本。 |
| `vertex_key_type` | `"json" \| "api_key"`，默认 `json` | Vertex AI | `json` 表示渠道密钥是服务账号 JSON，并换取 Bearer access token；`api_key` 表示渠道密钥是 Google API key，并通过 URL 的 `key` 参数调用。 |
| `openrouter_enterprise` | `boolean`，默认 `false` | OpenRouter | 按 OpenRouter Enterprise 的 `{success,data}` 外层响应解析；普通 OpenRouter 响应不要开启。 |
| `claude_beta_query` | `boolean`，默认 `false` | Claude/Anthropic 兼容渠道 | 强制在上游请求 URL 增加 `beta=true`。它不同于 `anthropic-beta` 请求头。 |
| `allow_service_tier` | `boolean`，默认 `false` | OpenAI、Claude、Responses 兼容请求 | 是否允许客户端的 `service_tier` 继续传给上游。默认过滤，避免意外选择可能额外计费的服务层级。 |
| `allow_inference_geo` | `boolean`，默认 `false` | Claude | 是否允许 `inference_geo` 透传。默认过滤，避免未经确认改变数据驻留区域。 |
| `allow_speed` | `boolean`，默认 `false` | Claude | 是否允许 `speed` 透传。默认过滤，避免意外切换推理速度模式。 |
| `allow_safety_identifier` | `boolean`，默认 `false` | OpenAI | 是否允许 `safety_identifier` 透传。默认过滤，避免在未明确授权时把用户标识发送给上游。 |
| `disable_store` | `boolean`，默认 `false` | OpenAI Responses 等 | 这是反向开关：`true` 时删除客户端的 `store` 字段；`false` 时允许原值透传。启用可能影响依赖上游存储的 Codex/Responses 工作流。 |
| `allow_include_obfuscation` | `boolean`，默认 `false` | OpenAI Responses 流式请求 | 是否允许 `stream_options.include_obfuscation` 透传。默认过滤，避免客户端关闭上游流混淆保护。 |
| `disable_task_polling_sleep` | `boolean`，默认 `false` | 视频及通用任务轮询 | `true` 时跳过同一渠道内逐个任务查询之间的 1 秒间隔。它不会关闭后台轮询周期；大量任务时可能更容易触发上游限流。 |
| `aws_key_type` | `"ak_sk" \| "api_key"`，默认 `ak_sk` | AWS Bedrock | `ak_sk` 使用原有 AK/SK 签名方式；`api_key` 选择 Bedrock API-key 模式，当前渠道密钥格式要求为 `<api-key>\|<region>`。 |
| `upstream_model_update_check_enabled` | `boolean`，默认 `false` | 支持模型列表查询的渠道 | 开启上游模型变化检测。Advanced Custom 渠道开启时必须配置 `/v1/models` 管理路由。 |
| `upstream_model_update_auto_sync_enabled` | `boolean`，默认 `false` | 已开启模型检测的渠道 | 自动把新发现模型加入渠道模型列表。只有检测开关同时开启时生效；不会自动删除上游已移除的模型。 |
| `upstream_model_update_last_check_time` | `integer`，默认 `0` | 模型检测 | 系统维护的最后检测 Unix 秒时间戳，不建议手工填写。 |
| `upstream_model_update_last_detected_models` | `string[]`，默认空 | 模型检测 | 系统维护的“待加入模型”列表，不建议手工填写。自动同步成功后会清空已加入项。 |
| `upstream_model_update_last_removed_models` | `string[]`，默认空 | 模型检测 | 系统维护的“上游已不存在、待人工确认删除”列表。系统不会据此自动删除本地模型。 |
| `upstream_model_update_ignored_models` | `string[]`，默认空 | 模型检测 | 不提示加入的模型规则。元素可以是精确模型名，也可以用 `regex:<正则>`，例如 `regex:^experimental-`。 |
| `advanced_custom` | 对象，默认不存在 | Advanced Custom 等高级自定义渠道 | 声明入口路径、上游路径、协议转换、模型选择和鉴权。详见本页第 6 节。部分内置高级渠道类型会使用代码中的固定预设覆盖该值。 |
| `upstream_async` | 对象，默认不存在 | 部分异步图片和视频渠道 | 动态提取上游任务号、构造轮询请求并解析状态、结果和用量。详见本页第 7 节。 |
| `ollama_openai_chat` | `boolean`，默认 `false` | Ollama | `true` 时 Chat 使用 OpenAI 兼容 `/v1/chat/completions`；`false` 时使用 Ollama 原生 `/api/chat` 并执行协议转换。Completion 的 `/api/generate` 不受影响。 |
| `tool_loss_policy` | `"allow" \| "safe" \| "strict"`，默认 `allow` | 跨协议请求转换 | 控制请求阶段的工具语义损失：`allow` 允许并记录诊断；`safe` 只拒绝会改变工具执行语义的严重损失；`strict` 拒绝所有有损转换，包括仅展示元数据丢失。响应和流转换不会因该字段被拒绝。 |

顶层未知字段目前不会产生业务效果，不应依赖它们。`upstream_async` 内部采用严格字段校验，拼错字段会在保存时直接报错。

## 3. 请求字段透传开关

以下六个开关只在“请求整包透传”关闭时负责过滤字段：

- 全局 `PassThroughRequestEnabled` 开启，或渠道 `setting.pass_through_body_enabled=true` 时，请求 JSON 会直接通过，上述字段过滤开关不会生效。
- `allow_service_tier`、`allow_inference_geo`、`allow_speed`、`allow_safety_identifier`、`allow_include_obfuscation` 都是“默认禁止，显式允许”。
- `disable_store` 相反，是“默认允许，显式禁止”。

适合 Claude 渠道的示例：

```json
{
  "allow_service_tier": true,
  "allow_inference_geo": true,
  "allow_speed": false,
  "claude_beta_query": true,
  "tool_loss_policy": "safe"
}
```

适合希望禁止上游存储、但允许安全标识的 OpenAI Responses 渠道示例：

```json
{
  "disable_store": true,
  "allow_safety_identifier": true,
  "allow_include_obfuscation": false
}
```

## 4. 供应商密钥模式示例

这些字段只切换密钥解释和协议模式，秘密值仍放在渠道“密钥”字段，不要写进 `settings`。

### Vertex AI API key

```json
{
  "vertex_key_type": "api_key"
}
```

此时渠道密钥填写 Google API key。使用服务账号 JSON 时省略该字段或设为 `json`。

### AWS Bedrock API key

```json
{
  "aws_key_type": "api_key"
}
```

此模式下渠道密钥按 `<api-key>|<region>` 填写。使用 AK/SK 时省略该字段或设为 `ak_sk`。

### OpenRouter Enterprise

```json
{
  "openrouter_enterprise": true
}
```

只有上游真实返回 Enterprise 外层结构时开启，否则普通响应会被误判为无效响应。

### Ollama OpenAI Chat

```json
{
  "ollama_openai_chat": true
}
```

仅当当前 Ollama 或其代理确实提供 `/v1/chat/completions` 时开启。

### Azure Responses 版本覆盖

```json
{
  "azure_responses_version": "<目标 Azure 端点支持的 api-version>"
}
```

尖括号内容必须替换成真实版本，不能原样提交。

## 5. 上游模型变化检测

推荐只配置三个管理员输入字段，其余 `last_*` 字段交给系统维护：

```json
{
  "upstream_model_update_check_enabled": true,
  "upstream_model_update_auto_sync_enabled": false,
  "upstream_model_update_ignored_models": [
    "legacy-model",
    "regex:^experimental-"
  ]
}
```

行为说明：

1. 系统从上游模型列表与渠道当前模型列表计算新增项和移除项。
2. 精确忽略规则或 `regex:` 规则命中的新增模型不会进入待处理列表。
3. 自动同步只添加新模型，不自动删除模型；移除项保存在 `upstream_model_update_last_removed_models`，由管理员确认。
4. Advanced Custom 渠道必须增加 `incoming_path: "/v1/models"` 的管理路由；该路由的 `models` 必须为空、`converter` 必须为 `none`，且不能启用请求体透传。
5. 检查会受服务端最小间隔限制；强制检测接口除外。

## 6. `advanced_custom` 完整说明

### 6.1 结构

```json
{
  "advanced_custom": {
    "advanced_routes": []
  }
}
```

`advanced_routes` 至少包含一条路由。每条路由字段如下：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `incoming_path` | `string`，必填 | new-api 接收的路径，必须以 `/` 开头且不能带查询字符串。Gemini 路径可使用一次 `{model}`。 |
| `upstream_path` | `string`，必填 | 上游目标。以 `/` 开头时拼接渠道 Base URL；也可以填写完整的 HTTP(S) URL。支持 `{model}`，替换为渠道模型映射后的上游模型名。 |
| `converter` | `string`，默认 `none` | 请求和响应协议转换器；必须与 `incoming_path` 匹配。见下表。 |
| `models` | `string[]`，默认空 | 该路由适用的客户端原始模型名（映射前）。支持精确名称或 `re:<Go 正则>`；空数组是同一路径的兜底规则，必须放在该路径所有特定模型规则之后。按配置顺序匹配，避免语义重叠的正则。 |
| `auth` | 对象，可选 | 上游鉴权方式。省略时默认发送 `Authorization: Bearer <渠道密钥>`。 |
| `pass_through_body_enabled` | `boolean`，默认 `false` | 是否不解析请求体、直接转发。只允许 `none` 和 `jina_rerank_to_sglang` 转换器；`/v1/models`、余额查询等管理路由必须为 `false`。 |

### 6.2 `auth` 字段

| `type` | `name` / `value` | 行为 |
| --- | --- | --- |
| 省略整个 `auth` | 无 | 默认 `Authorization: Bearer <渠道密钥>`。 |
| `none` | 不需要 | 不自动附加路由鉴权。 |
| `header` | 必填 | 把 `value` 写入名为 `name` 的请求头。`value` 中的 `{api_key}` 会替换为渠道密钥。 |
| `query` | 必填 | 把 `value` 写入名为 `name` 的查询参数，同样支持 `{api_key}`。 |

不要把真实密钥硬编码在 `auth.value`，应使用 `{api_key}`。

### 6.3 可用转换器

| `converter` | 要求的 `incoming_path` | 作用 |
| --- | --- | --- |
| `none` | 任意已配置路径 | 不做协议转换。 |
| `jina_rerank_to_sglang` | `/v1/rerank` 或 `/rerank` | 把 Jina Rerank 请求转换为 SGLang Rerank。 |
| `anthropic_messages_to_openai_chat_completions` | `/v1/messages` | Claude Messages → OpenAI Chat Completions。 |
| `openai_chat_completions_to_anthropic_messages` | `/v1/chat/completions` | OpenAI Chat Completions → Claude Messages。 |
| `openai_chat_completions_to_openai_responses` | `/v1/chat/completions` | OpenAI Chat Completions → OpenAI Responses。 |
| `openai_responses_to_openai_chat_completions` | `/v1/responses` | OpenAI Responses → OpenAI Chat Completions。 |
| `openai_responses_to_gemini_generate_content` | `/v1/responses` | OpenAI Responses → Gemini GenerateContent。 |
| `gemini_generate_content_to_openai_chat_completions` | `/v1beta/models/{model}:generateContent` 等 Gemini 路径 | Gemini GenerateContent → OpenAI Chat Completions。 |
| `openai_chat_completions_to_gemini_generate_content` | `/v1/chat/completions` | OpenAI Chat Completions → Gemini GenerateContent。流式请求会切换到 `streamGenerateContent?alt=sse`。 |

可用于能力识别的标准入口包括 `/v1/chat/completions`、`/v1/responses`、`/v1/responses/compact`、`/v1/alpha/search`、`/v1/messages`、`/v1/rerank`、`/v1/images/generations`、`/v1/embeddings` 和 Gemini GenerateContent 路径。

### 6.4 OpenAI Chat 转 Gemini 示例

```json
{
  "advanced_custom": {
    "advanced_routes": [
      {
        "incoming_path": "/v1/chat/completions",
        "upstream_path": "/v1beta/models/{model}:generateContent",
        "converter": "openai_chat_completions_to_gemini_generate_content",
        "models": ["re:^gemini-"],
        "auth": {
          "type": "query",
          "name": "key",
          "value": "{api_key}"
        }
      },
      {
        "incoming_path": "/v1/models",
        "upstream_path": "/v1/models",
        "converter": "none",
        "models": [],
        "auth": {
          "type": "query",
          "name": "key",
          "value": "{api_key}"
        }
      }
    ]
  },
  "upstream_model_update_check_enabled": true
}
```

`/v1/models` 的上游地址只是结构示例，必须改成供应商真实提供的模型列表路径；若供应商没有兼容模型列表接口，则不要开启自动检测。

### 6.5 无转换直通示例


## 7. `upstream_async` 完整说明

### 7.1 匹配与覆盖范围

```json
{
  "upstream_async": {
    "profiles": []
  }
}
```

- 最多 32 条 profile。
- 按 `media_type`、渠道映射后的上游模型名和标准化操作匹配。`models` 为空表示该渠道的全部上游模型。
- `operations` 使用 `generate`、`edit`、`extend`；图片不允许 `extend`。
- 同一媒体类型、模型和操作只能命中一条规则；空模型数组会与相同媒体/操作的任何模型规则重叠。
- 命中后覆盖任务号提取、轮询请求、状态、结果和 Usage 解析；`submit.request` 省略时沿用原渠道适配器或任务插件的提交请求，配置后由渠道规则构造同源 POST 请求。模型能力、计费钩子及展示仍由原适配器或任务插件负责。
- 未命中时继续使用渠道或任务插件的内置解析。
- 同步图片接口不会选择命中动态异步规则的渠道，应使用图片异步接口。

### 7.2 profile 字段

| 字段 | 类型与限制 | 含义 |
| --- | --- | --- |
| `id` | `string`，1–64 字符 | 管理员可读的唯一规则 ID，不能带首尾空格。 |
| `media_type` | `image` 或 `video` | 规则处理的媒体类型。 |
| `models` | `string[]`，最多 128 | 渠道模型映射后的上游模型名；空数组为全部模型。 |
| `operations` | `string[]` | `generate`、`edit`、`extend` 的非空组合；图片不能包含 `extend`。 |
| `submit.task_id_path` | 受限 GJSON 路径 | 从上游提交响应提取字符串或数字任务号。 |
| `submit.request` | 对象，可选 | 自定义首次提交请求；省略表示沿用内置提交。 |
| `poll.request` | 对象 | 如何查询同一个上游任务。 |
| `poll.response` | 对象 | 如何把查询响应归一化为本地任务状态、结果和 Usage。 |

### 7.2.1 `submit.request`

| 字段 | 类型与默认 | 含义 |
| --- | --- | --- |
| `method` | `POST`，必填 | 上游异步任务提交方法。 |
| `path` | `string`，必填 | 以单个 `/` 开头的路径，不能包含查询或片段；与渠道 Base URL 拼接，最终请求须与 Base URL 同源。提交前不能使用 `{task_id}`。 |
| `query` | `Record<string,string>`，可选 | 提交请求的查询参数模板，自动进行 URL 编码。 |
| `headers` | `Record<string,string>`，可选 | 提交请求头模板；常用 `"Authorization": "Bearer {api_key}"`。禁止覆盖 `Host`、`Content-Length`、`Connection`、`Transfer-Encoding`、`Upgrade`、`Proxy-Authorization`。 |
| `body` | JSON 对象，可选 | 提交 JSON 模板。省略时沿用适配器或插件构造的请求体；配置后按模板生成 JSON，适用于原请求体为 JSON 的路径。 |

路径、查询参数、请求头和普通字符串值支持下文的 `{model}`、`{upstream_model}`、`{api_key}`；提交前不能使用 `{task_id}`。提交 JSON 字段值还可使用完整的 `{request.prompt}`、`{request.image_urls}`、`{request.create_count}` 等受限路径，从已解析的客户端请求中复制原 JSON 类型；引用字段不存在时省略对应对象字段，数组元素引用缺失则拒绝提交。`{request.*}` 必须独占字符串值，不能嵌入其他文本。图片数量和视频时长字段会再次与已校验请求对照，避免模板绕过计费边界。

图片接口仍须匹配图片渠道能力及平台策略；视频接口仍须有任务插件认领该模型。`submit.request` 只替换上游 HTTP 提交请求，不负责新增模型能力。高级 JSON 保存后，同一 profile 的 `submit.task_id_path` 和 `poll` 仍需与供应商实际响应一致。

### 7.3 `poll.request`

| 字段 | 类型与默认 | 含义 |
| --- | --- | --- |
| `method` | `GET` 或 `POST`，必填 | 轮询方法。GET 不允许配置 `body`。 |
| `path` | `string`，必填 | 必须是以单个 `/` 开头的相对路径，不能包含查询或片段；相对于任务提交时冻结的渠道 Base URL。 |
| `query` | `Record<string,string>`，可选 | 查询参数模板。 |
| `headers` | `Record<string,string>`，可选 | 查询请求头模板。禁止覆盖 `Host`、`Content-Length`、`Connection`、`Transfer-Encoding`、`Upgrade`、`Proxy-Authorization`。 |
| `body` | 任意 JSON，可选 | POST 查询体；字符串值中可以使用允许的占位符。 |

允许的模板占位符只有：

| 占位符 | 值 |
| --- | --- |
| `{task_id}` | `submit.task_id_path` 提取的任务号；在 `path` 中会进行路径转义。 |
| `{model}` | 客户端请求中的原始模型名。 |
| `{upstream_model}` | 渠道模型映射后的上游模型名。 |
| `{api_key}` | 当前冻结渠道密钥。建议用它代替硬编码秘密。 |

`{task_id}` 仅在上游接单并返回任务号后的轮询与下载模板中可用。

### 7.4 `poll.response`

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `status_path` | 是 | 取得上游状态的受限 GJSON 路径。 |
| `status_values.queued` | 否 | 映射为本地排队状态的值。 |
| `status_values.in_progress` | 否 | 映射为本地处理中状态的值。 |
| `status_values.succeeded` | 是，至少一个 | 映射为本地成功状态的值。 |
| `status_values.failed` | 是，至少一个 | 映射为本地失败状态的值，包括供应商的取消、过期等终态。 |
| `progress_path` | 否 | 字符串会限长保存；0–100 的数字会格式化为百分比。 |
| `failure_reason_path` | 否 | 字符串失败原因，经限长和脱敏后写入本地失败任务。 |
| `result_path` | 是 | 成功结果路径。图片可返回一个 URL 字符串或 URL 字符串数组，最多 128 个；视频必须是单个 URL 字符串。URL 必须是 HTTP(S)。 |
| `usage_paths` | 否 | “本地 Usage 字段 → 上游响应路径”的映射。数值必须是 0 到 `int32` 上限之间的整数。 |
| `download_headers` | 否 | 下载结果时附带的请求头模板。只要配置了下载头，初始结果 URL 就必须与渠道 Base URL 同源；初始跨域结果必须不配置下载头并可匿名访问。 |

同源鉴权下载端点可以返回 HTTP 跳转到公网 CDN。跨域跳转后渠道下载头会被清除，目标地址仍按公网访问规则校验；不要把渠道 API Key 写进结果 URL。图片下载遇到 HTTP 408、429、5xx 或传输中断会按瞬时失败预算重新轮询并下载；视频保存失败会按媒体存储预算重试，动态规则在重试时重新查询上游任务以刷新签名 URL。两类任务都必须先完成本站媒体校验与存储，不会把上游 URL 直接返回给客户端。

状态值只能是非空字符串、数字或布尔值，并按 JSON 类型精确比较：字符串 `"1"`、数字 `1` 和布尔值 `true` 是三个不同状态。四组状态值不能重复或重叠。未知或缺失状态不会被当作“处理中”，而是进入现有轮询失败预算。

受限 GJSON 路径只允许简单对象键、数组序号和 `#` 数组投影，例如：

```text
data.task_id
data.items.0.url
data.items.#.url
usage.total_tokens
```

不支持过滤表达式、脚本、花括号或任意 GJSON 修饰器。

### 7.6 异步图片多结果示例

假设上游提交返回：

```json
{"data":{"task_id":"img_123"}}
```

查询成功返回：

```json
{
  "data": {
    "status": "succeeded",
    "progress": 100,
    "images": [
      {"url": "https://cdn.example.com/a.png"},
      {"url": "https://cdn.example.com/b.png"}
    ]
  },
  "usage": {"prompt_tokens": 24, "total_tokens": 24}
}
```

渠道配置：

```json
{
  "upstream_async": {
    "profiles": [
      {
        "id": "vendor-image",
        "media_type": "image",
        "models": ["vendor-image-v2"],
        "operations": ["generate", "edit"],
        "submit": {
          "task_id_path": "data.task_id"
        },
        "poll": {
          "request": {
            "method": "GET",
            "path": "/v1/tasks/{task_id}",
            "headers": {
              "Authorization": "Bearer {api_key}"
            }
          },
          "response": {
            "status_path": "data.status",
            "status_values": {
              "queued": ["pending", "queued"],
              "in_progress": ["processing", "running"],
              "succeeded": ["succeeded"],
              "failed": ["failed", "cancelled", "expired"]

            "failure_reason_path": "data.error.message",

              "total_tokens": "usage.total_tokens"

    ]
  }
}
```

`models` 匹配的是渠道模型映射后的名称。如果客户端请求 `public-image`，而渠道模型映射把它改成 `vendor-image-v2`，这里应填写 `vendor-image-v2`。

### 7.6.1 Mai Token 生图提交到视频路径

Mai Token 提供的接口文档使用 `POST /v1/videos` 创建图片任务、`GET /v1/videos/{task_id}` 查询。正式环境的 `seedream-5-pro` 完成响应实际返回 `metadata.url`，应从该字段取得图片地址；文档示例中的 `video_url` 不一定存在。渠道 Base URL 填 `https://api.mai-token.com`，规则的媒体类型仍填 `image`。以 `seedream-5-pro`、单张图片为例：

```json
{
  "upstream_async": {
    "profiles": [
      {
        "id": "mai-token-image",
        "media_type": "image",
        "models": ["seedream-5-pro"],
        "operations": ["generate"],
        "submit": {
          "task_id_path": "id",
          "request": {
            "method": "POST",
            "path": "/v1/videos",
            "headers": {"Authorization": "Bearer {api_key}"},
            "body": {
              "model": "{upstream_model}",
              "prompt": "{request.prompt}",
              "aspect_ratio": "{request.aspect_ratio}",
              "quality": "1440p",
              "image_urls": "{request.image_urls}",
              "create_count": "{request.create_count}"
            }
          }
        },
        "poll": {
          "request": {
            "method": "GET",
            "path": "/v1/videos/{task_id}",
            "headers": {"Authorization": "Bearer {api_key}"}
          },
          "response": {
            "status_path": "status",
            "status_values": {
              "queued": ["queued"],
              "in_progress": ["in_progress"],
              "succeeded": ["completed"],
              "failed": ["failed", "cancelled"]
            },
            "progress_path": "progress",
            "failure_reason_path": "error.message",
            "result_path": "metadata.url"
          }
        }
      }
    ]
  }
}
```

客户端继续调用 `/v1/images/generations_async`，例如传入 `model: "seedream-5-pro"`、提示词、`aspect_ratio: "16:9"`、一张可由 Mai Token 拉取的公开参考图 URL 和 `create_count: 1`。此示例把清晰度固定映射为供应商接受的 `1440p`；客户端的 `resolution: "2K"` 不会原样转发为 Mai Token 的 `quality`。图片模型、渠道、平台策略、计费以及任务结果存储仍须配置。查询响应的实际结构若与示例不同，应按真实响应调整状态和结果路径。

图生图还需把对应图片平台策略中该模型的 `max_reference_images` 设置为供应商允许的数量；Mai Token 文档给出的 `seedream-5-pro` 上限为 8。若设为 0，一张参考图也会在本地被拒绝。提交响应中的任务号位于顶层 `id`，状态位于顶层 `status`，本次实测结果位于 `metadata.url`。客户端收到 `query_url` 后应以 **GET** 请求 `/v1/media/tasks_async/{task_id}` 并携带原 Token；对该地址发送 POST 会命中未注册路由。

### 7.7 异步视频单结果与 POST 查询示例

```json
{
  "upstream_async": {
    "profiles": [
      {
        "id": "vendor-video",
        "media_type": "video",
        "models": ["vendor-video-model"],
        "operations": ["generate", "edit", "extend"],
        "submit": {
          "task_id_path": "request.id"

        "poll": {
          "request": {
            "method": "POST",

            "headers": {
              "Authorization": "Bearer {api_key}"
```

视频成功后，上游 URL 只保存在私有任务数据中。Worker 会下载、校验并写入现有媒体存储，本地任务查询最终返回 new-api 的签名结果 URL，而不是直接泄露上游 URL。

### 7.8 需要鉴权下载的同源结果

只有结果地址与渠道 Base URL 的协议、主机和有效端口完全同源时，才能配置下载请求头：

```json
{
  "download_headers": {
    "Authorization": "Bearer {api_key}",
    "X-Task-ID": "{task_id}"
  }
}
```

这是 `poll.response` 的子对象片段，不是完整 `settings`。如果供应商返回独立 CDN 或对象存储域名，必须省略 `download_headers`，并让该 URL 本身是可匿名访问的短期签名 URL。

## 9. 排错清单

| 现象 | 优先检查 |
| --- | --- |
| 保存时报 profile 重叠 | 是否存在空 `models` 规则与具体模型规则覆盖了相同媒体类型和操作。 |
| 提交后变成 `execution_unknown` | `submit.task_id_path` 是否指向真实字符串/数字任务号；提交响应是否为合法 JSON。此状态不会自动重新提交上游。 |
| 自定义提交返回 400 或未发出请求 | 检查 `submit.request.path`、鉴权头、JSON 模板、模型能力和已校验数量/时长；Mai Token 的图片提交需使用其 `/v1/videos` 路径及该模型支持的 `quality`。 |
| 视频返回 `Model has no capability for this video operation` | 该错误发生在上游提交前；先确认视频模型由任务插件认领并声明对应操作。图片模型应使用图片异步端点及 `media_type: "image"`。 |
| 一直提示未知状态 | `status_path` 是否正确；状态的 JSON 类型是否与配置一致；是否遗漏供应商的大小写或数字状态。 |
| 上游显示成功但本地解析失败 | `result_path` 是否只在成功响应存在；图片结果是否为字符串或字符串数组；视频是否只返回一个字符串 URL。 |
| 跨域下载被拒绝 | 是否错误配置了 `download_headers`；带渠道凭据的下载只允许同源。 |
| 图片成功但报 `billing_usage_missing` | 当前价格是否按 Token 结算；最终查询响应是否配置并返回有效 `usage_paths`。 |
| 同步生图找不到渠道 | 命中 `upstream_async` 的图片渠道是异步专用，应调用 `/v1/images/generations_async` 或 `/v1/images/edits_async`。 |
| 字段透传开关看起来无效 | 是否启用了全局请求透传，或在 `setting` 中启用了 `pass_through_body_enabled`。这两者会绕过字段过滤。 |
| Advanced Custom 路由不匹配 | `advanced_routes[].models` 匹配客户端原始模型名；`upstream_path` 的 `{model}` 才使用映射后的上游模型名。再检查入口路径、特定模型路由顺序、正则 `re:` 前缀和兜底路由位置。 |

## 10. 安全与维护建议

- 密钥只放渠道密钥字段；模板中使用 `{api_key}`，不要把真实密钥写进 `settings`、Wiki、日志或工单。
- 优先通过渠道编辑页保存，服务端会校验枚举、路径、重叠规则、模板、状态和结果限制。
- 修改在途异步任务的渠道设置不会改变已冻结任务所使用的 profile 和渠道快照。
- 测试新规则时先使用单个模型和单个操作，确认提交、轮询、失败、结果落盘和计费后再扩大 `models` 或 `operations`。
- 上游返回的原始任务号、原始轮询响应和结果 URL 都属于私有中间数据；对外只应使用现有任务查询和本地签名结果地址。
