本教程把“用户请求 A，符合分辨率和秒数条件时交给指定 E 渠道执行”拆成可照填的步骤。**渠道 49 和渠道 22 只沿用前轮读取时的示例编号，管理员必须重新核对名称、启用状态、分组、插件、模型和映射；它们不代表当前生产配置已经核验或生效。**

## 1. 配完后会发生什么

主例规则：用户不指定 `provider`，请求公开模型 `seedance2.5-A`，原分辨率为 `480p` 或 `720p`，时长满足 `15 < seconds ≤ 30`，则优先交给指定 E 渠道，并以 `720p` 执行。

| 项目 | 主例填写／预期 |
| --- | --- |
| 用户请求的公开模型 | `seedance2.5-A` |
| 原请求分辨率 | `480p` 或 `720p` |
| 原请求秒数 | 16–30 的整数；15 秒不命中 |
| 指定目标渠道 | 示例 `#49`，使用前重新核对 |
| 目标渠道声明的模型别名 | `seedance2.5-E` |
| 目标渠道内部模型映射 | `seedance2.5-E → seedance2.5-yx-count` |
| 实际执行分辨率 | 显式选择 `720p` |
| 向用户计费 | 仍按 A、原分辨率、原秒数及原分组计价 |
| 目标耗尽 | 本例选“任务失败”；也可逐规则改为“回退原路由” |

例如 A／480p／20 秒命中后，上游执行 E 对应模型／720p／20 秒，用户仍按 A／480p／20 秒原价结算。E 的按次成本不会自动成为用户售价，执行规格提高也不会把本次用户收费改成 A 的 720p 价格。

本功能作用于未指定 `provider` 的 `POST /v1/videos/generations_async` 混合异步生成。显式指定供应商、同步 `/v1/videos`、编辑和延长入口均不应用这些规则。规则不会自动让同步请求变成异步请求。

## 2. 先准备源 A，再配置目标 E

### 2.1 检查运行环境和管理入口

打开 **系统设置 → 运营设置 → 媒体设置**，直接路径为 `/system-settings/operations/images`。在其中选择“视频配置”。必须已有可用的视频异步运行环境：全局视频开关、任务插件、Redis、请求加密密钥、媒体签名与结果存储等。首次接入按[异步视频基础配置](05-异步视频与统一媒体任务.md)完成。

管理接口沿用后台管理认证及媒体配置权限：当前路由要求根管理员角色（`RootAuth`），读取／预览要求 `image_config:read`，保存要求 `image_config:manage`。后台登录会话的 access token 或根管理员已有的有效 PAT 可用于管理认证；普通模型调用 API Key 不等于这些管理凭据。只有读取权限时不能保存或修改规则。

在“视频平台策略”卡片中，将“供应商”切换为 **混合调度（mixed）**。只有选择 mixed 时，页面才显示“混合视频定价”和“视频条件路由”卡片；选择 Drama 或 yuxibox 时看不到该规则编辑区。

### 2.2 配置公开 A 的目录与原渠道池

先确保以下条件都成立：

1. A 原渠道能够接受原始请求，声明 `seedance2.5-A`，属于实际请求分组，模型能力与账号可用。示例源渠道可以是前轮提到的 `#22`，但不能仅凭编号认定它当前可用。
2. 相应分组的 mixed 视频平台策略已启用，支持异步执行，并在视频模型目录声明公开 A。
3. mixed 的原渠道池能够为 A 找到可验证原请求的源渠道，具有请求的分辨率、时长和素材能力。
4. 请求 Token 有权调用公开 A，分组及渠道约束允许此次请求。

在“视频模型目录”的现有数组中加入以下条目；**保留现有其他模型，不要用单条示例覆盖整份目录**：

```json
{
  "id": "seedance2.5-A",
  "label": "seedance2.5-A",
  "media_type": "video",
  "video_overrides": {}
}
```

目录是一个 JSON 数组，单条对象应放入已有 `[...]`。`video_overrides` 只能收紧插件能力，不能凭空扩展能力。完成后点击“保存视频策略”。

随后在媒体设置的“渠道池”页签核对相同分组、`mixed`、视频的池绑定。池绑定方式应与视频策略一致；例如使用“模型与分辨率”时，A 的 480p／720p 对应池档位 **1K**，1080p 对应 2K。这里的 1K 是池选择档位，不会把用户请求改成另一种视频分辨率。

**条件规则不是绕过源 A 配置的捷径。** 仅添加 E 目标而没有 A 的公开目录、原池或原请求验证能力，请求仍不能通过。源 A 不接受的素材格式、时长或提示词，也不会因为目标 E 更宽松而自动获得授权。

### 2.3 确认 A 的原售价

在 mixed 视频配置下查看“混合视频定价”，选择公开模型 `seedance2.5-A`：

- 使用“模型定价”时，A 必须已有启用且兼容 mixed 视频用量字段的模型计费表达式。
- 使用“自定义混合视频价格”时，保存 A 的专用 mixed 表达式；该显式覆盖优先。
- 如果价格只写在 `drama::seedance2.5-A` 等插件专属覆盖中，不会自动当作 mixed 的公开 A 售价。可使用已有价格复制入口，将兼容表达式复制到公开 mixed 草稿，核对后单独保存。

检查 480p／720p 单价、秒数单位、无／有参考视频条件及分组倍率。缺少兼容公开价格时请求会失败，不会静默改收 E 的价格。计费配置与表达式说明见[视频计费配置](09-视频计费配置.md)。本教程不提供未经核实的金额。

### 2.4 核对目标渠道的别名和实际模型

在 `/channels` 中查看准备作为目标的渠道。以示例 `#49` 为例，应核对：

| 渠道字段／状态 | 本例需要的内容 |
| --- | --- |
| 渠道启用与账号 | 渠道启用，并存在可用账号 |
| 渠道分组 | 包含实际请求使用的分组，例如 `default` |
| 任务插件 | 加载并启用可支持目标模型的插件；本例为 `yuxibox` |
| 渠道模型列表 | 声明别名 `seedance2.5-E` |
| 模型映射 | 将该别名映射到 `seedance2.5-yx-count` |

与本例对应的映射片段为：

```json
{
  "seedance2.5-E": "seedance2.5-yx-count"
}
```

这是**渠道的模型映射**，不是条件规则 JSON；合并到已有映射时也应保留其他条目。在规则的“目标模型”里选择渠道声明的 `seedance2.5-E`，下拉会展示 `seedance2.5-E → seedance2.5-yx-count`。不要因看到映射后名称，就把一个未在渠道模型列表声明的名称填成目标别名。

本地 yuxibox 插件对 `seedance2.5-yx-count` 声明的是 **5–30 秒、仅 720p**，4 秒不支持。别名叫 E 不会放宽这一限制。Drama 插件的同名 E 声明了不同的分辨率能力，不能拿它代替 yuxibox 的能力判断；以渠道实际加载的插件和完整请求校验为准。

目标 E 不要求成为公开 A 原池中的普通候选，也不要求把 E 另建成 mixed 的公开模型目录条目。但它仍必须满足目标渠道分组、启用模型、可用账号、调用方渠道约束和插件能力要求。

## 3. 在界面照填主例

在“视频配置”选择 mixed 后，展开 **视频条件路由 → 配置视频路由规则**，点击“添加路由规则”。

| 表单字段 | 首次照填 | 含义 |
| --- | --- | --- |
| 规则名称 | `A 长视频转 E 720p` | 便于管理员识别，可自定义 |
| 分组 | `default` | 只匹配此实际路由分组；使用其他分组时改成真实值 |
| 请求模型 | `seedance2.5-A` | 用户提交的公开模型，可在选择器创建精确名称 |
| 输入分辨率条件 | 同时选 `480p`、`720p` | 匹配原请求分辨率；同一维度多选表示任一值 |
| 生成模式 | `text_to_video`（文生视频） | 先验收最简单模式；其他素材模式按第 6 节扩展 |
| 参考视频 | `none`（无） | 本例不含参考视频；不等于所有素材都必须为空 |
| 最小时长（秒） | `15` | 下界值 |
| 不包含下限 | 勾选 | 表示严格大于 15 |
| 最大时长（秒） | `30` | 上界值 |
| 不包含上限 | 不勾选 | 表示小于等于 30 |
| 目标 1：渠道 | 选择核验后的 `#49` | 下拉按所选分组列出可用视频渠道 |
| 目标 1：目标模型 | `seedance2.5-E → seedance2.5-yx-count` | 保存的是渠道别名 `seedance2.5-E` |
| 目标 1：输出分辨率 | `720p` | 原 480p 被改写，原 720p 保持相同规格 |
| 目标耗尽后 | `任务失败` | 严格控制不回到成本更高的原池 |

点击弹窗的 **“应用到草稿”**，这一步只把规则放入当前页面草稿，尚未保存服务器。确认列表内该规则的启用框已勾选，并勾选页面的 **“启用视频条件路由”** 总开关。先按第 5 节预览，确认后点击 **“保存路由规则”**，看到保存成功才算持久化。

总开关和单条规则都必须启用。规则复制、上移／下移、启停、删除及目标排序都先修改页面草稿，也必须点击“保存路由规则”。视频平台策略、混合价格、渠道池和条件路由各自保存；一个保存按钮不会替其他卡片保存。

若只想处理原 720p，删除输入条件中的 480p，并可把目标输出选为“保持请求分辨率”。若保留 480p 条件且目标仅支持 720p，就必须显式选 720p；否则该目标不能执行原 480p 请求。

## 4. 条件、优先级和多目标怎么理解

不同维度之间是 **AND**，同一维度的多个选项是 **OR**。例如分组匹配，并且模型为 A，并且分辨率为 480p 或 720p，并且秒数大于 15 且不超过 30，才会命中。

空选择表示该维度不限，包括“请求模型”留空会覆盖所有公开模型。为避免扩大影响，本例明确填写 A 和分组。秒数可只设下界或上界；整数范围为 1–3600，但目标插件通常有更小范围。本例仍受 5–30 秒目标能力约束。没有边界值时，不能勾选相应“不包含”选项；没有任何整数落入区间的配置会被拒绝。

规则按列表从上到下选择**第一条命中的启用规则**。把更具体的规则放前面。预览可列出多条命中并提示重叠，但执行时第一条的目标耗尽后，不会继续尝试第二条规则。

一条规则可以配置 1–20 个目标，按目标顺序选择；全局最多 100 条规则。选择“添加目标”后先选另一个渠道，再选它声明的模型别名和输出分辨率；目标有自己的上移、下移和移除按钮。

**同一规则的目标渠道编号不得重复，即使目标模型不同也不允许。** 当前复用按渠道区分的“同渠道／换渠道”重试机制。需要两个候选时，请选择两个独立渠道；不要把同一渠道的 E、F 两个模型伪装成两次换渠道。

候选出现在下拉中，只代表目前能列为配置候选。保存和执行还会验证实际分组、模型、账号及能力；执行前渠道被停用或授权被撤销时，旧快照不会继续授予使用权限。自动分组请求应按最终实际路由分组检查规则，而不是仅看 Token 表单中写的 `auto`。

## 5. 用草稿预览检查，不发生成请求

在同一规则卡片下方填写“路由预览”：

| 预览字段 | 主例 |
| --- | --- |
| 分组／平台／媒体类型 | `default`／`mixed`／视频 |
| 执行方式 | 异步 |
| 模型 | `seedance2.5-A` |
| 分辨率 | 先 `480p`，再测 `720p` |
| 操作／模式 | `text_to_video` |
| 时长 | 先 20，再测 15、16、30 |
| 显式供应商（可选） | 留空 |
| 参考视频 | 无 |
| Token ID | 可填需要核对的实际 Token ID；留空仅按当前分组上下文预览 |

预览使用当前页面草稿，所以总开关在草稿中也需要打开。应看到命中规则、原请求与计费规格 A／480p／20 秒、目标渠道及映射后模型、执行 720p、目标可用或排除原因。原 720p／20 秒也应命中；15 秒不应命中本规则。

规则卡片内的预览携带当前草稿；媒体设置顶部独立“路由预览”页签读取已保存规则。预览不会保存草稿。非法结构应返回 400，即使草稿总开关关闭或源池暂时缺失，也不能把它视作有效草稿；失效渠道等实时依赖则作为目标排除原因显示，便于诊断。

预览**不调用上游、不生成视频，也不提供实际扣费金额报价**。它检查路由维度和声明能力，不能验证真实图片／视频／音频内容、供应商素材获取、提示词引用、实际生成质量和上游库存。看到“已选中”或“配置允许”不能代替带真实素材的完整请求验收。

已明确选择“有参考视频”时，源模型与目标模型的所选模式都必须声明视频输入能力；仅支持参考图片的目标会被排除。选择“无参考视频”也不能通过要求必填视频的模式。留空表示此维度未知，不代表已验证素材兼容。

如果同时命中多条规则，预览按顺序显示；检查首条是否就是预期规则。如果预览默认值有歧义，明确填写秒数、分辨率等字段。实际请求也先按源 A 能力规范化默认值，不能借目标 E 的默认值决定原 A 的匹配和计费。只有源请求存在可能命中的规则时才要求各源能力的计价默认值一致；所有规则都不可能匹配时保留原路由默认行为。自动分组按各组自身源能力判断，不借另一个组的默认值匹配本组规则。

## 6. 参考素材与分辨率改写

首次文生视频通过后，可复制规则，按目标实际声明的能力选择或放开素材模式；有参考视频时选择 `video`，要覆盖无／有参考视频可同时选两者或留空。规则条件变化不会自动转换素材协议。

本例 `seedance2.5-yx-count` 当前声明 `text_to_video` 与 `reference_to_video`，**未声明首尾帧模式**；不能仅在规则中勾选 `first_last_frame` 就让它支持首尾帧。普通参考图也应按目标的参考素材协议完整校验。需要首尾帧或其他目标未声明的模式时，配置真正支持该模式的另一目标，或保留原路由。

需要同时满足源 A 与目标 E 的完整请求要求：提示词引用、素材数量、类型、顺序、角色、首尾帧和选项都必须合法。例如源 A 对参考图提示词的 `@图1`／`@图片1` 要求仍然有效；目标不要求此格式也不能让不合法的 A 请求通过。

规则只改执行模型及显式指定的执行分辨率，原秒数、宽高比和素材语义保留。JSON 与 multipart 请求沿用原编码，上传文件不会因改写被丢弃。显式像素尺寸按比例缩放且要求精确整数结果，例如 `1920x1080 → 1280x720`；缩放后还必须被系统识别为目标分辨率规格，不能只看短边数字或结果是否为整数。不能精确保留比例、或缩放后不被识别为目标规格的改写会拒绝该目标，不会偷偷裁剪或四舍五入。素材不兼容时按候选和耗尽策略处理，不会通过删掉素材来强行生成。

“执行 720p”表示请求给供应商的执行规格，不等同于已经探测成品文件的实际像素尺寸；是否返回符合规格的文件仍需成品验收。

如果输入分辨率不限、选择了更高规格，或多选里含高于目标的分辨率，例如 1080p→720p，目标编辑区会提示“部分命中的请求可能会降为此分辨率，仍按原请求分辨率计费。”这表示可能降低用户实际获得的规格，管理员应明确核对规则范围。本例480p／720p→720p不属于降级，不显示该提醒。

## 7. 失败、回退与收费边界

“目标耗尽后”是**每条规则独立**的选择：

界面新建规则默认选择“回退原路由”。本教程主例为了限制成本，要求明确手动改成“任务失败”，不能把主例的严格选项当作新规则默认值。已有／复制规则保持自身的选择；通过 API 保存时，每条规则仍须明确填写 `on_exhausted`。

| 选项 | 行为 | 适合的取舍 |
| --- | --- | --- |
| 任务失败（`fail`） | 该规则没有可用目标时失败，不回原池，也不级联后续规则 | 不接受回到昂贵 A 渠道 |
| 回退原路由（`original`） | 恢复原 A 请求、原分辨率，回原混合渠道池；仍受原池权重与权限约束 | 可接受成本上升以提高可用性 |

回退原路由不是固定返回 `#22`；实际会按 A 原池配置选择。480p 转 E／720p 失败后回原池时，恢复 A／480p，不把 E 的分辨率改写带回 A。原池也不可用时仍然失败。

请求尚未发往上游时，目标失效可以跳过并选择后续冻结目标；已经调用上游后，是否同渠道重试或换渠道，还必须由现有错误与重试规则、次数／容量预算及结果确定性允许。配置多个目标不会增加重试预算。

**条件混合任务结果未知、已有输出，或已被上游接受但尚未终态时，不得通过换目标重新生成；应先查询／核对。** 明确失败的后续换目标才按现有规则处理。普通非混合任务的既有自定义重试行为不因本功能改变，详见[错误与重试规则](13-异步媒体错误与重试规则.md)。

已受理任务保留原计费和路由快照，修改规则／售价主要影响之后的新任务；当前渠道授权仍会实时检查。预扣、结算、退款沿用原 A 冻结价格和幂等账务链，不能通过变更目标重复扣费或重复退款。关闭总开关不会自动取消或重新定价已受理任务。

## 8. 冲突、失效草稿与安全停用

读取配置时会得到 `revision`，保存必须带读取时的修订号。另一管理员先保存后，本页旧草稿再保存会收到 **409 冲突**；页面保留草稿，要求显式重新加载。先记录需要保留的编辑，再加载最新配置、合并并检查，不能仅手改修订号强行覆盖别人改动。

保存尚未返回时在站内切页再返回，页面会等待同一次保存完成：成功后采用新修订，失败或冲突时恢复提交草稿并显示对应错误。保存失败、冲突或重新加载失败都不等于草稿已写入服务器。刷新整个浏览器页面仍可能丢失未保存编辑，请先保存或自行保留。

总开关开启时，启用规则必须通过目标的实时依赖校验。渠道被删除／停用后，如需先停止条件路由，可以关闭总开关再保存；此时仍做结构校验，但允许保留失效目标作为草稿。单条禁用规则也可保留结构合法的失效草稿。重新开启总开关或相关规则时会再次校验，不会把失效目标自动恢复。

保存只接受专用路由接口，不能通过通用 option 写入口绕过修订号。最大请求体为 1 MiB；省略的匹配数组在保存／读取后规范成 `[]`，含义仍是不限。

## 9. 用户和管理员分别看到什么

普通用户的任务详情和统一媒体查询仍显示公开模型 A，并能看到“请求分辨率”和“执行分辨率”的差异，例如 480p／720p。结果查看与下载沿用正常任务结果接口；内部 E 模型、执行平台／渠道、完整上游响应和规则诊断不作为条件任务的普通详情返回。

查询条件任务时，使用受理响应给出的公开查询地址。通用任务查询隐藏执行平台；OpenAI 视频查询保留标准身份、状态、规格和可用的结果链接，不透传供应商扩展对象。公开失败信息只保留服务端归类的原因与建议，重试排队、核对状态和过期清理后的错误也不会直接带出内部执行型号。条件任务的供应商原生查询入口返回 404，不能通过更换查询路径获取内部响应；正常结果查看与下载不受此限制。

管理员可看到规则 ID／名称／修订、源模型与执行模型、目标顺序及跳过原因、当前目标和是否回退原路由。任务日志 DTO 的完整规则信息位于 `admin_info.video_routing`，统一媒体管理员任务视图提供 `video_routing`。原始请求详情仍以 A 的原参数为准。

历史无规则任务不补造路由审计。未生成原生任务且请求密文已经清理的过期／失败任务，无法可靠重建规则详情；普通视图对执行平台信息采用保守隐藏，管理员仍可排查原记录。

## 10. API 配置示例

以下仅为**本地隔离／mock 服务**示例，地址统一用 `http://127.0.0.1:18080`；尖括号中的认证值均为不可用占位，不含密码、Cookie 或可用 Token。首选直接在已登录的根管理员后台完成配置，浏览器客户端会处理当前后台 access token。当前管理中间件读取 `Authorization: Bearer ...`，接受有效后台会话 access token 或已有 PAT，并核验用户角色／权限；不能仅携带旧式 Cookie、用户 ID，或用普通模型调用 Key 代替。mock 环境可以模拟认证，真实服务必须通过正常认证，不应关闭鉴权。

| 方法与路径 | 作用 |
| --- | --- |
| `GET /api/option/images/video-routing-rules` | 取得完整配置与最新修订号 |
| `GET /api/option/images/video-routing-rules/options?group=default` | 列指定分组的启用视频渠道及模型别名／映射 |
| `GET /api/option/images/video-routing-rules/options` | 不指定分组，列全部可配置候选；不免除执行时的实际分组检查 |
| `PUT /api/option/images/video-routing-rules` | 带修订号完整保存配置 |
| `POST /api/option/images/routing/preview` | 预览已保存配置或提交的草稿 |

先读取，不要猜测修订号：

```bash
curl --fail-with-body \
  'http://127.0.0.1:18080/api/option/images/video-routing-rules' \
  --header 'Authorization: Bearer <LOCAL_ROOT_PAT_OR_DASHBOARD_ACCESS_TOKEN>'

curl --fail-with-body \
  'http://127.0.0.1:18080/api/option/images/video-routing-rules/options?group=default' \
  --header 'Authorization: Bearer <LOCAL_ROOT_PAT_OR_DASHBOARD_ACCESS_TOKEN>'
```

全新未保存配置的 `data` 通常为 `{"version":1,"revision":0,"enabled":false,"rules":[]}`。下面文件 `routing-save.json` 演示主例；**只有 GET 确认当前 revision 为 0 才能使用示例里的 0**。已有配置时，保留最新 `version`／`revision` 和其他规则，合并本条后再保存；PUT 是整份替换，不是追加单条。

```json
{
  "version": 1,
  "revision": 0,
  "enabled": true,
  "rules": [
    {
      "id": "a-long-to-e-720",
      "name": "A 长视频转 E 720p",
      "enabled": true,
      "match": {
        "groups": ["default"],
        "models": ["seedance2.5-A"],
        "resolutions": ["480p", "720p"],
        "modes": ["text_to_video"],
        "video_inputs": ["none"],
        "seconds": {
          "min": 15,
          "max": 30,
          "min_exclusive": true,
          "max_exclusive": false
        }
      },
      "targets": [
        {
          "channel_id": 49,
          "model": "seedance2.5-E",
          "resolution": "720p"
        }
      ],
      "on_exhausted": "fail"
    }
  ]
}
```

规则 `id` 应稳定且唯一；界面新增时自动生成。`resolution: ""` 才是保持原分辨率。没有秒数边界时省略 `min`／`max`，对应 exclusive 字段为 `false`。

```bash
curl --fail-with-body --request PUT \
  'http://127.0.0.1:18080/api/option/images/video-routing-rules' \
  --header 'Authorization: Bearer <LOCAL_ROOT_PAT_OR_DASHBOARD_ACCESS_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data-binary @routing-save.json
```

成功响应的 `data.revision` 是保存后的新修订号，下次编辑必须以新值为基准。缺少修订号返回 428，旧修订号冲突返回 409，结构或能力校验错误一般返回 400；不能把这些结果当成已保存成功。

预览已保存配置的示例文件 `routing-preview.json`：

```json
{
  "group": "default",
  "platform": "mixed",
  "media_type": "video",
  "execution_mode": "async",
  "operation": "text_to_video",
  "mode": "text_to_video",
  "model": "seedance2.5-A",
  "resolution": "480p",
  "seconds": 20,
  "video_input": "none"
}
```

要预览尚未保存的草稿，在该对象里增加 `video_routing_config`，值为上方完整配置对象；UI 会自动携带当前草稿。返回结果的 `conditional_routing` 包含 `matched_rules`、`source`、`targets`、`selected_target_index`、`on_exhausted` 等；数组下标从 0 开始。未命中时不应据此推断一定有可用原渠道，应同时查看预览的原路由结果和原因。

```bash
curl --fail-with-body --request POST \
  'http://127.0.0.1:18080/api/option/images/routing/preview' \
  --header 'Authorization: Bearer <LOCAL_ROOT_PAT_OR_DASHBOARD_ACCESS_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data-binary @routing-preview.json
```

下面的生成示例也只用于本地 mock 上游联调，不含 `provider`；这里换用模型调用 Key 的占位值，不能与管理 PAT 混用。真实生成会触发任务与费用，需在获准的验收环境中另外安排：

```bash
curl --fail-with-body --request POST \
  'http://127.0.0.1:18080/v1/videos/generations_async' \
  --header 'Authorization: Bearer <LOCAL_RELAY_API_KEY>' \
  --header 'Content-Type: application/json' \
  --data '{"model":"seedance2.5-A","prompt":"A quiet sunrise over a lake","seconds":20,"resolution":"480p","aspect_ratio":"16:9"}'
```

使用受理响应返回的任务 ID／查询地址查询，不要把 `seedance2.5-yx-count` 改成用户请求模型来代替规则验证。显式加上合法 `provider` 后应按该供应商原路由处理，条件路由不介入。

## 11. 配置验收表

先做预览，再在有授权的本地 mock 或验收环境做提交／查询／结果／账务联调。下表“应有结果”建立在源 A 原请求合法、目标与价格配置正确的前提下。

| 检查 | 应有结果 |
| --- | --- |
| A／480p／15 秒，无 provider | 不命中主例，按原路由处理 |
| A／480p／16 秒，无 provider | 命中主例，执行 E／720p，按 A／480p／16 秒收费 |
| A／720p／30 秒，无 provider | 命中主例，执行720p，按原A参数收费 |
| A／31 秒 | 超过主例上界；如果源A自身能力也不支持31秒，请求直接被拒绝，不会因未命中规则而放行 |
| A／1080p／20 秒 | 不命中本例分辨率条件；是否可执行由原路由决定 |
| 显式 provider | 条件规则绕过；仍须满足显式供应商自身要求 |
| 用 4 秒请求验证 yx-count 目标能力 | 目标拒绝4秒；主例本身也不会匹配4秒 |
| 关闭总开关或禁用该规则并保存 | 新请求不使用该条件规则 |
| 两条规则都匹配 | 只有第一条参与目标选择；预览提示重叠 |
| 排队后首目标被停用，存在合法第二目标 | 派发前重新验证，按冻结次序选择后续目标 |
| 全部目标失效且策略为 fail | 失败，不回昂贵原池 |
| 全部目标失效且策略为 original | 用原A、原480p等参数返回原池 |
| 已接受未终态／结果未知／已有输出 | 先核对，不换目标重放 |
| 480p→720p 成功结算 | 只按原A480p价计费；没有目标按次价替换或额外扣一次 |
| 普通／管理员分别查看 | 普通保留公开A和两种分辨率；管理员能看规则与执行目标 |
| 两个页面读取同修订号后先后保存 | 后保存的旧草稿收到409，不覆盖先保存者 |
| 保存后切走再返回规则页面 | 显示已保存的新规则与修订，不回到保存前的缓存 |
| 保存仍在进行时切页再返回 | 等待原保存；200采用新修订，409／500恢复提交草稿与错误 |
| 手机用键盘空格启停规则 | 状态按预期变化，焦点仍停留在操作控件，可继续键盘操作 |
| 键盘把规则／目标移动到列表边界或删除规则 | 焦点留在可操作的控件，可继续编辑 |
| 预览选择有参考视频，目标所选模式仅支持图片 | 排除该目标；源组同样必须具备视频输入能力 |
| 仅有参考模式规则，实际是无素材文生视频且省略秒数 | 不因不匹配规则额外触发源默认值歧义错误 |

本地冒烟的实际执行结果与命令记录在[首次补充冒烟](14-2026年11月代码变更台账.md#conditional-video-routing-guide-smoke-20261104)及[再次冒烟](14-2026年11月代码变更台账.md#conditional-video-routing-resmoke-20261104)。测试通过只证明所覆盖的本地场景，不代表渠道 49／22 的当前生产配置或真实厂商生成已经验收。

## 12. 常见问题排查

| 现象 | 先检查什么 |
| --- | --- |
| 找不到“视频条件路由” | 是否打开媒体设置的“视频配置”，并把供应商选为 mixed；本机／服务器是否运行含本功能的版本，是否有配置权限 |
| 列表里有规则，请求仍不命中 | 页面总开关、单条开关是否都已保存；是否误传 provider；实际分组、模型大小写、原分辨率、15秒边界、模式与参考视频条件是否一致 |
| 下拉找不到渠道49或标不可用 | 重新核对实际编号、启用状态、分组、任务插件、模型别名和插件生成能力；别用手写旧ID绕过 |
| 找得到E但没有预期映射 | 检查渠道模型列表和模型映射；目标保存别名，不凭名称推测实际供应商 |
| 源模型不可用／模型未允许 | 检查A公开mixed目录、源池、Token模型权限与分组；单有E目标不够 |
| 预览目标允许，但带素材实际失败 | 预览没有验证真实素材内容；检查A提示词引用、角色与顺序，以及E的输入协议、数量、素材可访问性和选项 |
| 480p匹配后目标不可用 | 仅720p目标是否显式选择输出720p；像素比例是否可精确保留 |
| 默认值有歧义 | 显式提交原seconds／resolution等值；核对原池各源能力默认值，不使用目标默认值替代 |
| 提示目标耗尽／无兼容目标 | 在管理员诊断查看渠道、模型、分组、账号、映射／插件变更或请求校验原因；再核对fail/original选择 |
| 回退后仍失败 | 原池还必须有合法候选与账号；回退不是无条件保证成功 |
| 关闭功能也保存失败 | 关闭总开关后外部失效依赖可作为草稿保存，但名称、重复渠道、秒数范围、结构和修订号仍必须合法 |
| 收费与预期不符 | 查原A公开价格、mixed显式覆盖、原分辨率／秒数／参考视频条件及分组倍率；修改只影响新受理任务，不用E成本推算用户价格 |
| 409／428 | 重新读取revision并合并；不是渠道故障，不要重复发送旧配置 |

## 13. 上线与后续改规则的建议顺序

本节只说明操作顺序，不代表已经执行或得到发布授权。

1. 备份当前规则、源平台策略、渠道池、渠道映射和价格配置，记录部署版本与修订号。
2. 在本地隔离环境完成本页验收；需要真实厂商素材或质量验证时，先单独确认付费测试范围。
3. 获得针对本次版本与目标环境的明确发布命令后，再按部署方案发布前后端，说明是否重启／停机、请求影响和回退方案。不能仅靠上传插件代替宿主功能发布。
4. 由获授权管理员核对线上实际渠道编号与原A条件。已保存配置的总开关先保持关闭，核对源A目录、原池和售价；只在尚未保存的页面草稿中打开总开关，使用规则卡片内预览检查条件路由。预览完成前不保存启用状态；实际开启并保存线上业务规则也需要对应授权。
5. 先限定一个分组、一个模型和已验收模式；用获准的小范围生成检查用户规格、管理员执行审计、结果和账务，再扩大模式或分组。
6. 出现问题时，关闭总开关并保存使新请求恢复既有路由；已受理任务仍按其快照和核对机制处理。不要重跑未知结果的历史任务来验证修复。

后续只改条件或目标时无需改调用方公开模型，但仍需检查能力、原价与修订冲突。规则关闭、原路由回退和代码版本回滚是不同操作，不能相互替代。
