## Cyber Landing 首页

公开首页拆分为 `CyberLanding` 组件，并通过独立样式文件提供完整视觉系统。

主要行为：

- 根据登录状态显示“开始使用”或“进入控制台”入口。
- 模型网络中心 `cyber-core` 自动读取 `/api/status` 的站点名称（`system_name`）展示；未配置时回退为默认站点名。
- 放大中心品牌与“统一 API 网关”副标题字号，避免小屏下副标题难以辨认；过长站点名在核心区内省略显示。OpenAI 节点展示品牌标识，不再用字母 O 代替图标。
- 展示统一模型网关、图像与音频能力、渠道和计费管理能力。
- 提供 API 协议介绍、终端演示和能力流程。
- 顶部与首页「文档」入口指向站内 `/docs`，不再跳转外部文档站点。
- 提供动画暂停/恢复控制，并兼顾键盘焦点、减少动态效果偏好和响应式布局。
- 首页装饰动效包括背景网格漂移、纵向扫描光带、粒子、网络雷达扇面、核心脉冲、节点浮动、集成区扫光、协议标签呼吸、步骤分隔光迹和底部透视网格流动。粒子层标记为 `aria-hidden`，不改变标题和网络插图的无障碍名称；暂停与 `prefers-reduced-motion` 会停止这些动画。
- 新增首页组件测试并补齐七种语言。

## Fork Docker 部署工具

目录：`deployment/fork-docker/`

### 运行组成

- new-api 应用容器。
- PostgreSQL 15。
- Redis 7 Alpine。
- 本地 `data`、`logs`、`images`、`postgres-data` 和 `redis-data` 持久化目录。
- 应用、PostgreSQL 和 Redis 健康检查。
- JSON 文件日志轮转。

### 脚本

- `install.sh`：检查依赖和 HTTPS 域名，克隆指定 Fork，生成随机密钥，构建镜像并首次启动。
- `compose-env.sh`：统一 Docker Compose 项目名、配置文件和环境加载。
- `manage.sh`：提供 `status`、`version`、`logs`、`start`、`resume`、`restart`、`backup` 和 `update`。
- `update-confirm.sh`：独立的交互式更新入口，在构建成功后、停服备份前等待人工确认，保留原 `manage.sh` 行为。
- `export.sh`：导出离线部署所需源码、镜像或工具材料。
- `restore.sh`：根据备份恢复数据库、Redis 和运行文件。

<a id="update-confirm"></a>

### 编译完成后确认停服更新

新脚本先检查部署状态、拉取 `https://github.com/JasonWangJie/new-api.git` 的 `main`，并构建对应提交的镜像。原应用在拉取、构建及等待确认期间继续运行；构建仍会占用服务器的 CPU、内存和磁盘。

首次使用时，将本地脚本单独上传到部署目录。在本地 PowerShell 执行，替换 SSH 用户、服务器地址，以及实际工作区路径：

```powershell
scp "F:\Code\Git\new-api\deployment\fork-docker\update-confirm.sh" root@你的服务器:/opt/new-api/update-confirm.sh
```

然后登录服务器执行（通过 `bash` 运行，无需另设可执行权限）：

```bash
bash /opt/new-api/update-confirm.sh
```

如果服务器源码中已经存在此脚本，也可以从服务器源码复制后运行，不必单独上传：

```bash
cp /opt/new-api/src/deployment/fork-docker/update-confirm.sh /opt/new-api/update-confirm.sh
bash /opt/new-api/update-confirm.sh
```

脚本不更新部署目录中的旧 `manage.sh`；首次安装和离线导出工具目前不会自动携带这个独立脚本，应按上述步骤单独保存。不要为了取得脚本先运行原 `manage.sh update --ready`，因为原更新流程没有编译后的确认点。

出现“现在等待你的确认”后，可以继续等待其他任务完成，等待没有超时。脚本不会自动关闭任务入口或检查任务是否清空：确认前自行暂停新任务提交，检查已有任务的结果保存和结算均已完成，再输入完整的大写 `UPDATE` 并回车。不要将确认输入通过管道预先传入，否则会跳过人工等待。

- 输入 `UPDATE` 并回车：重新核对部署配置、原容器、构建镜像和源码，然后停服备份、切换到已经构建的提交、启动并检查实际发布端口的 `/api/status`。确认后不再拉取或重新构建其他提交。
- 输入其他内容（包括空行）或输入结束：退出且不停止服务；已拉取的源码与构建镜像保留。
- 确认前按 `Ctrl+C`，或进程收到 `TERM` / `HUP`（例如普通 SSH 断线）：中止且不进入停服阶段。使用 tmux/screen 时会按终端会话行为继续等待，但不会自行确认。
- 等待期间配置、原容器、镜像或源码变化：拒绝本次确认，需重新运行脚本。

脚本全程持有 `.manage.lock`，等待期间其他协作管理脚本的启动、备份、更新会被拒绝；不会锁住正常业务请求。备份沿用现有 PostgreSQL 转储、Redis 保存和运行文件归档步骤，跳过 `images`；只有存在 `COMPLETE` 标记才表示备份完成。部署目录中存在 `update-confirm.sh` 时也会收入运行文件归档。切换前失败时尝试恢复原应用及 Redis；镜像配置已经切换后不自动回退数据库，应检查日志处理。

自定义部署目录时：

```bash
NEWAPI_DEPLOY_DIR=/你的部署目录 bash /你的部署目录/update-confirm.sh
```

自定义 Compose 项目名时，沿用原部署使用的 `NEWAPI_PROJECT_NAME` 环境变量。

<a id="docker-build-cache-cleanup"></a>

### 发布成功后清理 Docker 构建缓存

`manage.sh update --ready` 和 `update-confirm.sh` 在新应用启动且 `/api/status` 返回 `success: true` 后，自动执行一次构建缓存清理，无需额外确认。先输出更新提交和备份位置，再清理缓存；清理时服务已经恢复运行。构建失败、取消确认、备份失败、启动或健康检查失败，以及源码无需更新时均不清理。

- Buildx 可用：执行 `docker buildx prune --all --force`，清理当前选中 builder（含 `BUILDX_BUILDER` 指定的实例）的可回收缓存，包括内部构建辅助缓存；不遍历其他 builder。
- 没有 Buildx：执行 `docker builder prune --all --force`，清理 Docker 引擎的全部未使用构建缓存。
- 清理失败：保留错误输出并提示中文警告，不触发发布失败处理，不回滚、不重启，退出状态仍表示本次更新成功。

命令含义参见 Docker 官方的 [Buildx 缓存清理](https://docs.docker.com/reference/cli/docker/buildx/prune/)和 [builder 缓存清理](https://docs.docker.com/reference/cli/docker/builder/prune/)。此步骤保留应用镜像（包括旧版本镜像）、运行容器、数据卷、图片和备份；不会执行 `docker system prune` 或镜像/数据卷清理。被镜像或正在进行的构建引用的内容可能仍占磁盘，不能保证释放全部 Docker 空间。清理后下次构建可能需要重新下载依赖、重新编译。当前 builder 与其他项目共用时，其可回收构建缓存也会被清理。

已有服务器使用的是 `/opt/new-api/` 下保存的脚本，拉取 `src` 不会自动替换它们。需要在没有管理脚本运行或等待确认时，将修改后的两份文件上传替换。以下仅为手动同步命令，替换 SSH 地址与本地路径后执行；该步骤不运行更新或重启服务：

```powershell
scp "F:\Code\Git\new-api\deployment\fork-docker\manage.sh" "F:\Code\Git\new-api\deployment\fork-docker\update-confirm.sh" root@你的服务器:/opt/new-api/
```

替换后继续使用原来的两个更新入口即可。北京时间 **2026-10-20 20:06:59** 已按用户本次上传指令，将两份脚本的缓存清理改动同步到 `40.160.139.185:/opt/new-api/`。服务器 `manage.sh` 与仓库版本有既存差异，本次只给远端原文件增加相同的 8 行清理逻辑，不覆盖其他行为；`update-confirm.sh` 同样仅增加 8 行。持有 `.manage.lock` 后复核旧哈希、保留权限和所有权并逐文件原子替换，两份脚本的 Bash 语法、新哈希和前后容器运行状态核对通过。

旧文件备份：`/opt/new-api/backups/scripts-cache-cleanup-20261020T120659Z-iBWVIX`，包含前后校验和、容器运行快照及 `COMPLETE` 标记。本次未执行应用更新、重启、构建或真实缓存清理；下次正常发布成功后自动清理。验证记录见[10 月台账](10-2026年10月代码变更台账.md#docker-build-cache-cleanup-change)。

### 更新与备份约束

- 写操作使用文件锁，避免安装、备份和更新并发运行。
- 更新前备份 PostgreSQL、Redis、运行文件、镜像标识和校验和。
- `manage.sh backup` 和 `update --ready` 的运行文件归档包含 `.env`、`image.env`、Compose 配置与脚本、`data`、`logs` 和 `redis-data`，跳过生成图片目录 `images`，缩短备份期间的停机时间。
- 图片继续通过 `./images:/images` 挂载持久化到服务器的部署目录，正常更新容器不会删除已有图片。上述日常备份不提供图片文件副本；完整离线备份或跨服务器迁移使用 `export.sh`，其归档仍包含 `images`。
- 备份只有存在 `COMPLETE` 标记时才视为完成。
- 应用仅绑定本机端口，外部访问由反向代理和受信任 HTTPS 地址提供。
- 更新失败时脚本尽量恢复尚未切换的服务；数据库已经迁移后不会自动执行破坏性回退。
