# 企业开票申请与历史补开

本页记录提交 `4ddaa904351d6b78c6370f817849d278de582b10` 引入的企业开票功能。完整提交清单见 [2026 年 9 月变更记录](02-2026年09月代码变更台账.md)。

## 功能范围

企业开票功能面向人民币易支付及实收大于 0 的人工后台充值订单，提供用户申请、管理员人工处理和历史补开台账。邮箱用于管理员线下发送发票；系统当前不自动开票、不上传发票附件，也不自动发送邮件。

## 用户流程

入口：`/wallet/invoices`

### 申请开票

1. 系统列出当前登录用户全部可开票的充值订单及付款方式。
2. 用户可以按充值订单号搜索、分页浏览并跨页勾选。全选只影响当前页，改变搜索条件会清空已选订单。
3. 页面显示已选订单数量、人民币合计和当前最低开票金额。
4. 第一次申请时，用户填写企业名称、企业税号和发票接收邮箱；后续申请会自动带入最近一次成功提交的企业资料。
5. 自动带入的资料仍可编辑；申请成功后，本次企业名称、企业税号和邮箱会成为下次申请的默认值。提交失败不会覆盖已保存的默认资料，并保留当前输入供用户重试。
6. 服务端重新读取订单、计算金额并检查提交时的最低金额配置，不采信客户端金额；订单状态发生冲突时刷新可选订单。

只有功能开关启用时用户才能提交新申请。关闭功能后，历史记录仍然可以查看，管理员仍可处理已有申请和进行历史补开。

### 开票记录

记录包含：

- 状态：待处理、已完成或已拒绝。
- 企业名称、企业税号和邮箱。
- 开票金额及关联充值订单；订单明细同时显示付款方式。
- 申请时间、处理时间、操作人。
- 拒绝原因或历史补开备注。

申请被拒绝后，只释放该申请占用的充值订单。旧申请和拒绝原因永久保留，用户可以重新选择这些订单，也可以与其他订单合并后再次申请。

## 管理员流程

入口：`/admin/invoices`

### 申请记录

- 可按用户 ID、用户名、显示名称、用户邮箱、企业资料或充值订单号搜索。
- 可按申请状态筛选，并查看企业资料、订单明细和付款方式。
- 待处理申请只能从 `pending` 转为 `completed` 或 `rejected`。
- 拒绝时必须填写原因；完成后订单继续保持占用。
- 处理结果、操作人 ID、操作人用户名快照和操作时间与业务记录在同一事务中保存，然后写入现有审计日志。

### 历史补开

1. 管理员通过用户 ID、用户名、显示名称或邮箱搜索并明确选定用户。
2. 系统列出该用户全部历史可开票订单及付款方式；切换用户会清空选择。
3. 管理员跨页勾选订单，可填写备注并确认标记已开票。
4. 系统直接创建来源为 `admin_history`、状态为 `completed` 的记录。

历史补开不要求企业资料，不受最低开票金额限制，并会出现在用户的开票记录中。

## 订单资格与金额

一笔订单必须同时满足以下条件：

- 属于目标用户。
- 充值状态为支付成功。
- 明确标记为易支付充值，或支付渠道为空且订单号符合旧版 `USR{用户ID}NO{6 位字母数字}{10 位时间戳}` 规则；也允许来源和付款方式均为 `manual_backend` 且私有交易快照有效的人工后台订单。
- 不属于订阅购买。
- 保存的支付金额有效且大于零。
- 没有被待处理或已完成的开票记录占用。

易支付订单沿用保存的人民币金额，格式化为两位小数后精确转换为整数分；人工后台订单直接读取确认时保存的实收人民币分金额，赠送订单不参与开票。合计过程检查整数溢出，任一订单无效或发生冲突时整批事务回滚。

大量跨页选择会分批执行数据库查询和写入，业务上不设置 100 单上限。

## 状态和数据表

### 状态流转

```text
pending ──> completed
   │
   └──────> rejected ──> 释放订单占用，可创建新申请
```

已完成和已拒绝记录不能再次变更状态。

### 数据表

- `invoice_requests`：申请或补开主记录，保存来源、企业资料、金额、状态、时间、拒绝原因、备注和操作人快照。
- `invoice_request_items`：保存每批充值订单的订单号、金额和时间快照。
- `invoice_order_claims`：以充值订单 ID 为主键建立唯一占用，防止用户申请与管理员补录重复开票。

付款方式不在开票明细表中重复保存。接口按 `top_up_id` 从充值订单读取支付成功后保存的实际付款方式；因此该展示不新增数据库字段或迁移。

默认企业资料也不新增数据表或字段。系统只读取当前用户最近一条来源为 `user` 的成功创建申请，管理员历史补开记录不会覆盖该资料。

开票功能不会修改充值支付状态或用户余额。

## 人工后台加额订单

### 操作入口和使用步骤

管理员入口：**用户管理（`/users`）→ 打开用户信息 → 调整额度**。

1. 选择“添加”，或选择“覆盖”并输入比当前余额更高的额度。额度输入继续沿用站点的 USD、人民币、自定义货币或 Tokens 显示设置。
2. 服务端按目标用户当前数据库余额计算实际净增加量；页面展示调整前后余额。
3. 正向加额会显示“实收金额（人民币）”和付款方式“人工后台”。建议金额按现有充值单价、**目标用户**分组充值倍率和精确匹配的折扣档位预填，管理员可改为实际收到的金额。人民币实收金额独立于额度显示货币；修改实收不会改变到账额度。
4. 确认后，余额调整和已完成订单在同一事务中保存。页面提示订单号。订单付款方式、来源均为 `manual_backend`，创建时间和完成时间相同。
5. 实收大于 0 的订单可以在 **钱包 → 企业开票（`/wallet/invoices`）** 申请开票，也可以在 **管理员 → 企业开票（`/admin/invoices`）→ 历史补开** 补录。
6. 实收为 0 时页面提示赠送订单：仍记录到账额度，不能申请或补录发票。扣减、覆盖后减少或不变只调整余额并保留审计，不生成订单。

人工加额本身不增加配置开关，也不依赖线上支付网关是否启用。建议金额沿用已有充值价格与分组倍率；用户新申请开票继续受企业开票开关、最低金额约束，管理员历史补开沿用原有规则。

超级管理员可从以下现有配置入口调整相关规则：

| 配置 | 页面路径 | 字段 |
| --- | --- | --- |
| 企业开票开关和最低金额 | `/system-settings/billing/invoice` | `payment_setting.invoice_enabled`、`payment_setting.invoice_min_amount_cents` |
| 人民币充值单价和折扣 | `/system-settings/billing/payment` | `Price`、`payment_setting.amount_discount` |
| 目标用户分组的充值倍率 | `/system-settings/billing/group-pricing` | `TopupGroupRatio` |
| 额度显示币种和换算单位 | `/system-settings/billing/currency` | `general_setting.quota_display_type`、`QuotaPerUnit` |

只为本功能启用后的新操作生成订单；此前只有加额日志的历史操作不会自动补造。充值记录中的人工订单显示精确的 USD 额度金额及人民币实收金额，开票按实收金额计算，后续更改充值价格、显示汇率或分组倍率不改变该订单。

### 重试、并发与权限

- 操作人身份来自管理员鉴权上下文，前端不能指定；普通管理员只能操作比自己角色低的用户，超级管理员沿用现有管理范围。
- 加额和订单任一步保存失败，事务都回滚，不出现“余额已增加但订单丢失”。
- 正向加额结果不明确时，弹窗保留原参数及幂等键，锁定编辑和关闭，显示“重试确认”。按原参数重试会返回原订单，不重复入账、增加缓存或记第二条额度变动日志。不要在结果未确认前刷新页面或另建请求。
- 覆盖操作提交时重新锁定并读取余额；实际净变化和预览不符（包括由增加变为减少或不变）时返回 `409`，无本次余额或订单变更。页面刷新预览，保留管理员已编辑的实收金额，再次确认。
- 同一幂等键按操作人和目标用户隔离，同参数重放返回原交易快照；已用键的参数发生变化返回 `409`，不能修改原订单。
- 人工订单不能进入用户在线支付选择，也不能被支付回调或管理员补单再次充值。审计关联订单号、实收分金额与重放标记。订单接口不返回操作人、幂等输入或私有快照；管理员通过既有审计入口查看操作信息。

### 额度调整 API

管理员鉴权与角色限制和 `/api/user/manage` 一致。预览接口只读取余额和报价，不生成订单、不加额。

```http
POST /api/user/quota/preview
Content-Type: application/json

{"id":42,"mode":"add","value":250000}
```

响应 `data` 包含 `before`、`after`、十进制字符串 `delta_quota`、`suggested_payment_amount_cents`、`payment_currency: "CNY"` 和 `payment_method: "manual_backend"`。其中 `value` 是原始额度单位，和既有管理接口相同；例如 `QuotaPerUnit = 500000` 时 `250000` 等于 0.5 USD 额度，建议实收按现有充值配置计算。

提交确认时：

```http
POST /api/user/manage
Content-Type: application/json

{
  "id": 42,
  "action": "add_quota",
  "mode": "add",
  "value": 250000,
  "payment_amount_cents": 1234,
  "idempotency_key": "28a9658d-3360-4a30-9535-ecbbdcb2e641",
  "expected_delta_quota": "250000"
}
```

上述操作到账 0.5 USD 额度、记录实收人民币 12.34 元。修改额度需要重新预览并创建新的 UUID；**同一次确认的网络重试必须复用原 UUID 和全部原参数**。

| 字段 | 规则 |
| --- | --- |
| `payment_amount_cents` | 实收人民币整数分，必填；`0` 为赠送，不能省略或传 `null`；负值无效 |
| `idempotency_key` | 标准小写、带连字符的 UUID，同一确认操作保持不变 |
| `expected_delta_quota` | 复制预览的净变化字符串，避免超过 JavaScript 安全整数时丢失精度 |
| `mode` / `value` | 沿用 `add`、`subtract`、`override` 和原始额度整数；最终余额维持现有钱包边界 |

正向加额缺少确认字段或字段无效返回 `400 / MANUAL_PAYMENT_INVALID`；预览失效或幂等参数冲突返回 `409 / MANUAL_QUOTA_CONFLICT`。旧脚本不再能仅凭 `id/action/mode/value` 正向加额，必须升级调用；扣减及覆盖后净不增加的旧请求保持兼容。非常大的实收金额还需能在现有订单 `Money` 字段中精确还原到分，不能依靠浮点舍入改变实收。

成功响应新增 `data`：`user_id`、`before`、`after`、`delta_quota`、`replayed`，正向加额还包含 `order`。重放返回第一次提交的快照，当前余额以重新查询用户信息为准。

人工订单 API 的 `amount` 保存原始正向额度增量；新增 `credited_quota`、`credited_amount` 字符串分别表示精确额度及创建时的 USD 额度金额，`payment_amount_cents` 是实收分金额，`payment_currency` 固定 `CNY`。人工订单应使用新增字段展示，不能把 `amount` 当成旧版在线订单的整数 USD 金额。既有线上订单字段含义不变。

数据库仅为主库 `top_ups` 增加可空 `TEXT` 列 `manual_adjustment`，保存创建时的余额、额度换算、实收及操作快照；没有新增订单表或修改日志库表。启动时通过既有 GORM 迁移增加该列，旧订单保持空值。三库迁移和流程验证、权限依据及具体命令见 [2026 年 10 月变更台账](10-2026年10月代码变更台账.md)。

## 配置与权限

计费设置包含：

- `payment_setting.invoice_enabled`：用户新申请开关，默认 `false`。
- `payment_setting.invoice_min_amount_cents`：最低开票金额，单位为人民币分，默认 `0`。

前端按人民币元展示和输入最低金额，支持两位小数。配置写入沿用超级管理员权限。

管理员接口使用以下权限：

- `invoice.read`：查看全站记录、详情和指定用户可开票订单。
- `invoice.manage`：完成、拒绝申请和创建历史补开记录。

两个权限默认授予管理员角色。

## API

### 用户接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/invoice/config` | 读取开关、最低金额和本人最近一次申请的企业资料 |
| `GET` | `/api/invoice/orders` | 查询本人可开票订单 |
| `POST` | `/api/invoice/requests` | 创建开票申请 |
| `GET` | `/api/invoice/requests` | 查询本人开票记录 |
| `GET` | `/api/invoice/requests/:id` | 查询本人记录详情 |

### 管理接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/invoice/admin/requests` | 查询全站开票记录 |
| `GET` | `/api/invoice/admin/requests/:id` | 查询记录详情 |
| `GET` | `/api/invoice/admin/orders` | 查询指定用户可开票订单 |
| `POST` | `/api/invoice/admin/requests/:id/complete` | 标记申请完成 |
| `POST` | `/api/invoice/admin/requests/:id/reject` | 拒绝申请 |
| `POST` | `/api/invoice/admin/history` | 创建历史补开记录 |

所有金额字段统一使用整数分。可开票订单和申请明细响应包含 `payment_method`。用户接口只使用当前登录用户身份，管理接口需要管理员身份及相应开票权限。
